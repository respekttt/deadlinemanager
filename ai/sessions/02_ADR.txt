  standards/adr/ і запиши цей промпт в ai/prompts-log.md (перевірка C11).       
                                                                                
  Рішення (контекст і альтернативи для кожного ADR):                            
                                                                                
  1. Runtime: Bun ≥ 1.3 (ESM) — замість Node.js, щоб мати в одному бінарнику    
  runtime, пакетний менеджер, тест-раннер і SQLite-драйвер. Це менше            
  залежностей і конфігурації, а також відповідає філософії «менше коду — менше  
  помилок».                                                                     
  2. HTTP: Fastify 5 — замість Express, бо в Fastify є вбудована валідація за   
  JSON Schema і app.inject(), що дає API-тести без запуску порту (spec §2,      
  tests). До того ж він має нативну підтримку ESM і async/await та менше        
  ручного boilerplate для обробки помилок.                                      
  3. БД: вбудований bun:sqlite — замість сторонніх ORM/драйверів (Sequelize,    
  better-sqlite3), щоб прибрати зовнішні залежності, зменшити ризик supply      
  chain attacks (перевірка C9) і отримати максимальну швидкість «з коробки».    
  Доступ до БД — лише з server/repositories і server/db (межі з spec §2,        
  перевірка C3).                                                                
  4. Тести: bun:test — замість Jest чи Mocha, щоб не встановлювати важкі        
  зовнішні бібліотеки й запускати тести миттєво без додаткових конфігурацій.    
  Покриття — вбудованим bun test --coverage з порогом у bunfig.toml (C6).       
  5. Лінтер: ESLint (через bunx) — замість Biome чи JSHint, бо це стандартний,  
  перевірений часом інструмент із найбільшою екосистемою правил і плагінів      
  (C2).                                                                         
  6. Форматер: Prettier (через bunx) — замість ручного форматування чи          
  застарілих форматерів, щоб повністю автоматизувати єдиний стиль коду й не     
  сперечатися на code review про відступи й лапки. Теж перевірений часом        
  інструмент із великою екосистемою (C1).                                       
  7. Межі модулів: dependency-cruiser — щоб автоматично перевіряти заборонені   
  залежності між шарами з spec §2 (domain, services, routes, repositories, db)  
  і не покладатися на дисципліну людини чи ШІ (C3).                             
  8. Git-хуки: власна тека .githooks + git config core.hooksPath, яку вмикає    
  скрипт prepare у package.json — замість Husky і замість ручних скриптів у     
  .git/hooks. Хуки поширюються через репозиторій і вмикаються автоматично на    
  bun install, без зайвої залежності (pre-commit = make check, pre-push = make  
  prepush).                                                                     
  9. Точка входу перевірок: Makefile — єдиний інтерфейс команд (make check /    
  prepush / ci) для розробника, хуків і CI, щоб усі запускали ті самі перевірки 
  однаковими командами.                                                         
  10. Валідація вхідних даних: Ajv (вбудований у Fastify 5) + JSON Schema —     
  замість ручної перевірки полів чи Joi/Zod. Схеми лежать у server/domain як    
  звичайні об'єкти без імпортів (межі spec §2, C3), Fastify перевіряє за ними   
  тіло й параметри запиту. Так немає окремої залежності, а перевірка            
  декларативна й однакова для всіх маршрутів. Правила, які JSON Schema не       
  виражає (довжина title після trim — AC-2, dueAt у майбутньому відносно        
  інжектованого now — AC-3), перевіряє код у server/domain. Помилки Ajv         
  мапляться у 400 VALIDATION_ERROR (spec §3). Альтернатива — окремий пакет ajv  
  + ajv-formats прямо в domain — відхилена як дублювання того, що вже дає       
  Fastify.

  Розбіжності. ADR я написав так, як ти описав. Ось що з цим не сходиться:

  1. ADR 0010 суперечить spec §2: routes може брати з domain лише класи помилок.
     Щоб Fastify перевіряв запит за схемами, routes має імпортувати ці схеми з
     server/domain. Тоді правило dependency-cruiser (C3, AC-15) або впаде, або
     його доведеться послабити. Що можна зробити:
     - дозволити в spec §2 імпорт domain/schemas;
     - реєструвати схеми в main.js і передавати їх у маршрути.
  2. ADR 0010 розходиться зі spec §5 S1. За spec вся валідація відбувається в
     domain після того, як routes передав тіло в команду. За ADR частину
     перевірок робить Fastify ще в routes. Про це етап у spec не згадує.
  3. Spec §5 S1 суперечить сам собі, і це зачіпає ADR 0010. Перевірку існування
     courseId (AC-4) spec відносить до «валідації в domain» через
     CourseRepository.findById. Але за §2 domain ні від чого не залежить і
     репозиторій викликати не може. Логічно, що це робить CreateTaskCommand у
     services. Тому в ADR 0010 я не вказав, де перевіряється AC-4.
  4. ADR 0003 каже «доступ до БД — лише з repositories і db», але server/main.js
     за spec §2 залежить від усіх модулів. Скоріше за все, саме він відкриває
     підключення. Це варто прямо вписати у формулювання.
  5. Запуск ESLint і Prettier «через bunx» не узгоджується з C8 і C9. Якщо їх
     немає в devDependencies, то bunx щоразу завантажує свіжу версію. Тоді bun 
     install --frozen-lockfile (C8) їх не фіксує, а bun audit (C9) їх не
     перевіряє. Простий вихід — тримати їх у devDependencies, а bunx
     використовувати лише для запуску. Як запускати dependency-cruiser, у
     документах не сказано.
  6. Дрібниця: README пише fastify.inject(), а spec §2 — app.inject().
