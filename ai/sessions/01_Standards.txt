❯ Створи файли README.md, definition-of-done.md, checklist.md, spec.md для      
  проєкту на тему:                                                              
                                                                                
  DeadlineHub — REST API для відстеження навчальних дедлайнів.                  
                                                                                
  Основні можливості:                                                           
                                                                                
  Створення задачі з назвою, курсом і терміном здачі (dueAt).                   
  Перегляд задачі за id та списку задач з фільтром за статусом і курсом.        
  Зміна статусу задачі лише за дозволеними переходами: todo → in_progress →     
  done (in_progress → todo дозволено, done — кінцевий).                         
  Сортування списку за терміном здачі, позначка прострочених задач (overdue).   
  Історія змін статусу задачі.                                                  
  (У наступних завданнях) нагадування про наближення дедлайну.                  
                                                                                
  Без авторизації: один студент, без користувачів і без колаборації. Без UI —   
  лише REST API (JSON).                                                         
                                                                                
  Обов'язковим є використання патернів state, strategy, observer, command,      
  repository наступним чином:                                                   
                                                                                
  State (Стан) — у домені:                                                      
  Кожен статус задачі (todo, in_progress, done) — окремий об'єкт стану, який    
  сам знає, в які статуси можна перейти. Недозволений перехід → помилка         
  валідації (HTTP 400).                                                         
                                                                                
  Strategy (Стратегія) — у сервісі списку:                                      
  Сортування та фільтрація списку задач через стратегії, наприклад              
  ByDueDateStrategy, ByStatusStrategy, OverdueOnlyStrategy. Нову стратегію      
  можна додати без зміни сервісу.                                               
                                                                                
  Command (Команда) — для історії змін:                                         
  Кожна зміна задачі (створення, зміна статусу) — об'єкт команди, який          
  виконується сервісом і записується в таблицю task_history.                    
                                                                                
  Observer (Спостерігач):                                                       
  Після зміни статусу сервіс повідомляє підписників: запис в історію і (у       
  наступних завданнях) планувальник нагадувань.                                 
                                                                                
  Repository (Репозиторій):                                                     
  Сервіси працюють з портом сховища (save, findById, list), а не з SQLite       
  напряму. Заміна сховища не торкається бізнес-логіки.                          
                                                                                
  База даних (SQLite):                                                          
                                                                                
  Створення задачі (tasks):                                                     
  Коли студент надсилає POST /tasks, бекенд валідує дані (title 3..120 символів 
  після trim, dueAt — майбутня дата, courseId — існуючий курс або null) і       
  створює запис у tasks зі статусом todo.                                       
                                                                                
  Зміна статусу та історія (task_history):                                      
  Коли студент надсилає PATCH /tasks/:id/status, бекенд знаходить задачу (404,  
  якщо немає), перевіряє перехід через State (400, якщо заборонено), оновлює    
  status і updated_at у tasks і в тій самій транзакції додає рядок у            
  task_history.                                                                 
                                                                                
  Нагадування (reminders) — лише в ER, реалізація в наступних завданнях:        
  Для задачі можна буде створити нагадування з часом спрацювання; планувальник  
  вибирає ті, що настали і ще не надіслані.                                     
                                                                                
  ```mermaid

      courses ||--o{ tasks : "містить"                                          
      tasks ||--o{ task_history : "має історію змін"

      courses {

      tasks {

      task_history {
  ```                                                                           

● Я перевів документи на Bun і Fastify.

  Що змінилося:
  - Runtime: Bun ≥ 1.3 замість Node.js.
  - HTTP: Fastify 5 замість Express, також у composition root і в правилах меж
    модулів.
  - БД: вбудований bun:sqlite замість node:sqlite, також у правилах меж модулів.
  - Тести: bun:test з app.inject() від Fastify. API-тести тепер не відкривають
    порт, тож fetch більше не потрібен.
  - Один критерій прийняття: make ac ID=AC-N тепер запускає bun test -t "AC-N:".
  - Покриття: bun test --coverage, поріг 80 % задається в bunfig.toml.
  - Встановлення і збірка: bun install (він же вмикає хуки) і bun install 
    --frozen-lockfile у make build.
  - Аудит залежностей: bun audit.

  Prettier, ESLint і dependency-cruiser я залишив і запускаю через bunx, бо
  вбудованого форматера, лінтера чи перевірки меж модулів у Bun немає.

  Що варто перевірити: у тестових прикладах я не перевіряв, як Bun запускає
  скрипт prepare під час bun install. Від цього залежить, чи вмикаються хуки
  самі. Якщо ні, знадобиться окрема ціль make hooks.

  Можна ще скоротити код: Fastify вміє перевіряти тіло запиту за JSON Schema.
  Перевірку типів можна віддати йому, а в domain залишити тільки бізнес-правила:
  trim, dueAt > now, чи існує курс. Тоді треба ще домовитися про єдиний формат
  помилки 400. Якщо хочете, внесу це в spec.

❯ Перевырь як Bun запускає скрипт prepare під час bun install                   

● Так, Bun 1.3.14 запускає скрипт prepare із package.json самого проєкту під час
  bun install. Отже, хуки вмикаються автоматично, і окрема ціль make hooks не
  потрібна.

  Я перевірив це на тестовому проєкті без залежностей, де prepare виконує git 
  config core.hooksPath .githooks:

  ┌─────────────────────────┬─────────────┬─────────────────────────────────┐
  │                         │     Чи      │                                 │
  │        Сценарій         │ виконався   │            Результат            │
  │                         │   prepare   │                                 │
  ├─────────────────────────┼─────────────┼─────────────────────────────────┤
  │ bun install (перший     │ так         │ core.hooksPath=.githooks        │
  │ запуск)                 │             │                                 │
  ├─────────────────────────┼─────────────┼─────────────────────────────────┤
  │ bun install (повторний) │ так         │ .githooks                       │
  ├─────────────────────────┼─────────────┼─────────────────────────────────┤
  │ bun install             │             │                                 │
  │ --frozen-lockfile (як у │ так         │ .githooks                       │
  │  make build і CI)       │             │                                 │
  ├─────────────────────────┼─────────────┼─────────────────────────────────┤
  │ bun install             │ ні          │ хуки не ввімкнулися             │
  │ --ignore-scripts        │             │                                 │
  ├─────────────────────────┼─────────────┼─────────────────────────────────┤
  │ bun install поза        │ так, але з  │ fatal: not in a git directory,  │
  │ git-репозиторієм        │ помилкою    │ встановлення падає з кодом 128  │
  └─────────────────────────┴─────────────┴─────────────────────────────────┘

  Останній випадок має значення, наприклад, для Docker-образу без .git. Тому я
  дописав у standards/checklist.md точний вигляд скрипту: git config 
  core.hooksPath .githooks || true. Завдяки || true встановлення не падає, а в
  репозиторії хуки, як і раніше, вмикаються.

  На проєкті з реальними залежностями і lock-файлом я не перевіряв, але
  --frozen-lockfile поводиться так само. Виняток — --ignore-scripts: хто
  встановлює з цим прапорцем, має ввімкнути хуки вручну командою git config 
  core.hooksPath .githooks.
