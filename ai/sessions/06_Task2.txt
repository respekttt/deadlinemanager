  інтерфейс — HTTP API (або UI-виклики). API покриває ВСІ основні сценарії, а   
  не один GET; схема БД без API прототипом не вважається.                       
  • Інтеграція БД: замінити статику реальною БД; транзакції, валідація, обробка 
  збоїв джерела, ідемпотентність/ретраї.                                        
  • Рівні декомпозиції: роути знають про HTTP; сервіси — про бізнес-операції й  
  доступи; SQL і транзакції — лише в репозиторіях/DAO. SQL чи транзакції в      
  роутах — порушення меж.

  ініціалізовані ресурси (БД), користувач-ініціатор, business-process ID.       
  Варіанти: DI, context-реєстр, AsyncLocalStorage / contextvars, Effect тощо —  
  вибір в ADR.

  будь-якого рівня, включно з операціями з БД та їхнім результатом, містить     
  ID, щоб за ним знайти всі операції одного запиту. Допустимі реалізації: (1)   
  явний контекст першим/останнім аргументом прикладних функцій; (2)             
  AsyncLocalStorage — один кореневий хук/middleware ініціалізує контекст, логер 
  читає з нього ID (~30 рядків, без змін решти коду); (3)                       
  команди/DI-контейнер, що підставляє прив'язаний логер. Протягування сирого ID

  ADR — standards/adr/0010-dependency-context-choice.md, за MADR:
  - Варіанти — ті самі три, що ви бачили в питаннях: AsyncLocalStorage, явний
    ctx і awilix. Для кожного є плюси й мінуси.
  - Decision Drivers прямо кажуть, що варіант запропонував AI, а обрали ви, і що
    рішення переглядатиметься.
  - Consequences містять і проблему на майбутнє: фоновий ReminderScheduler
    працюватиме поза запитом, тому йому знадобиться власний контекст.

  Що виправлено в spec (standards/spec.md). Це розбіжності, які я знайшов, коли
  писав ADR:
  1. Логер. Раніше логер мав отримувати ID через mixin у pino. Але сервіси не
     можуть імпортувати fastify, тому тепер у контекст запиту кладеться
     request.log.child({ userId }), а всі шари пишуть через log з
     server/context.js.
  2. Хто розпізнає збій БД. Помилки драйвера тепер перетворюються на
     SourceUnavailableError у репозиторіях, а не в роутах чи обробнику.
  3. Ідемпотентність. Ключ зберігається лише після успішного створення:
     невалідний запит його не займає. Це додано в AC-18.
  4. Порти й залежності. Додано порт IdempotencyRepository, а сервісам і
     репозиторіям дозволено імпортувати context.
  5. AC-23. ESLint не може надійно знайти SQL у коді роутів. Тому SQL у роутах
     перевіряє dependency-cruiser через заборону імпортів (C3), а ESLint лише
     забороняє try/catch.

  Обсяг spec скоротився з 204 до 138 рядків. ER-діаграма тепер показує лише
  зв'язки, а колонки перелічено в таблиці. Подробиці про контекст перенесено в
