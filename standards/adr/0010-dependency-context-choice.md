# AsyncLocalStorage для контексту запиту й логера, конструктор для ресурсів

- **Date:** 2026-11-20
- **Status:** accepted

## Context and Problem Statement

Завдання 2 (spec §2, §5) вимагає, щоб сервіси й репозиторії мали доступ до трьох речей: ініціалізованих ресурсів (БД, репозиторії, `now`), користувача-ініціатора (`X-User-Id`, spec §1) і business-process ID (`requestId`). Кожен рядок логу з будь-якого шару, включно з SQL-операціями та їхнім результатом, має містити `requestId` (AC-19). Водночас не можна протягувати 10–15 параметрів через усі виклики, а `services` не можуть залежати від `fastify` (spec §2, C3). Як доставити контекст і прив'язаний логер до глибоких шарів?

## Decision Drivers

- Вимога лаби: кожен рядок логу містить ID; ручне протягування сирого ID не рекомендується, а тега логера лише на рівні репозиторію недостатньо.
- Мінімум змін у сигнатурах і мінімум коду (філософія README: «менше коду — менше помилок»).
- Без нових залежностей (ADR 0003, перевірка C9).
- Межі шарів із spec §2 не порушуються: `services` не імпортують `fastify`.
- Варіант запропонував AI, користувач обрав його з трьох (слід: `ai/prompts-log.md`, сесія 8). Глибокого порівняння продуктивності не робили, тому рішення підлягає перегляду.

## Considered Options

- `AsyncLocalStorage` (`node:async_hooks`) + ресурси через конструктор
- Явний `ctx` першим аргументом прикладних функцій
- DI-контейнер зі scope на запит (`awilix`)

### `AsyncLocalStorage` + конструктор

- Добре, бо контекст ініціалізує один хук `onRequest` (~30 рядків у `server/context.js`), а сигнатури сервісів і репозиторіїв не змінюються.
- Добре, бо вбудований у Bun, без нових пакетів.
- Добре, бо логер береться з контексту, тому рядок, записаний будь-де в межах запиту, гарантовано має `requestId`.
- Погано, бо залежність неявна: з сигнатури функції не видно, що вона читає контекст.
- Погано, бо поза запитом (unit-тести сервісів, старт сервера) контексту немає, і потрібен fallback на кореневий логер.
- Погано, бо контекст губиться, якщо код виходить з async-ланцюжка (наприклад, сторонній колбек без збереження контексту). Ризик закриває AC-19.

### Явний `ctx` першим аргументом

- Добре, бо залежність видно в кожній сигнатурі, і тести передають `ctx` напряму, без магії.
- Добре, бо немає ризику втратити контекст в async-ланцюжку.
- Погано, бо змінює сигнатури всіх команд, сервісу, портів і репозиторіїв, а кожен новий виклик мусить не забути передати `ctx`.
- Погано, бо фактично це протягування контексту вручну, від якого лаба застерігає, лише згорнуте в один об'єкт.

### DI-контейнер `awilix` зі scope на запит

- Добре, бо контейнер сам підставляє прив'язаний логер і `userId` у конструктори scoped-сервісів.
- Добре, бо явна реєстрація залежностей в одному місці.
- Погано, бо це нова runtime-залежність (C9), а для одного сервісу й п'яти репозиторіїв це зайвий шар.
- Погано, бо сервіс і репозиторії доведеться створювати на кожен запит або реєструвати як scoped, що ускладнює `main.js` і тести.

## Decision Outcome

Обраний варіант: «`AsyncLocalStorage` + ресурси через конструктор», бо він єдиний виконує вимогу лаби до логера без зміни сигнатур і без нових залежностей.

- **Ресурси** (`db`, репозиторії, `transaction`, `now`) `main.js` один раз передає в конструктор `TaskService`. Вони не залежать від запиту, тому в контекст не потрапляють.
- **Контекст** — `server/context.js`, без імпорту `fastify`:
  - `als = new AsyncLocalStorage()`;
  - `getContext() → { requestId, userId, log } | undefined`;
  - `log` — проксі, що делегує в `getContext()?.log`, а без контексту — у кореневий логер, який `main.js` задає через `setRootLogger(app.log)`.
- **Ініціалізація** — хук `onRequest` у `main.js`: `als.run({ requestId: request.id, userId, log: request.log.child({ userId }) }, done)`. Де `userId = X-User-Id ?? 'anonymous'`.
- **ID запиту** — опції Fastify `requestIdHeader: 'x-request-id'`, `genReqId: () => crypto.randomUUID()`, `requestIdLogLabel: 'requestId'`. `request.log` уже прив'язаний до ID; хук `onSend` повертає `X-Request-Id`.
- **Хто що логує:** репозиторії — кожен SQL-виклик (`debug`: операція, тривалість, рядки або помилка); сервіс — бізнес-події (`info`); глобальний `setErrorHandler` — помилки (`warn` для 4xx, `error` для 5xx).

### Consequences

- Добре, бо `grep requestId=<id>` по логу дає всі операції одного запиту, від роуту до SQL (AC-19).
- Добре, бо `services` і `repositories` імпортують лише `server/context.js`, межі spec §2 не змінюються, крім дозволу на цей модуль (правило C3).
- Добре, бо unit-тести сервісів працюють без контексту (fallback-логер) або загортаються в `als.run(...)`, щоб перевірити `userId`.
- Погано, бо неявна залежність: читач `TaskService` мусить знати, що `userId` береться з `getContext()`. Компенсуємо тим, що контекст читають лише `context.js`, сервіс і репозиторії.
- Погано, бо `HistoryRecorder` викликається синхронно в межах запиту й отримує `userId` з контексту. Асинхронний `ReminderScheduler` у наступних завданнях працюватиме поза запитом і потребуватиме власного контексту (свій `requestId` на запуск).
- Переглянути, якщо з'являться фонові задачі або кілька сервісів: тоді, можливо, варто перейти на явний `ctx` для фонових процесів.
