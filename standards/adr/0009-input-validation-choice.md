# Валідація вхідних даних: Ajv у Fastify 5 + JSON Schema з server/domain

- **Date:** 2026-10-14

## Context and Problem Statement

API (spec §3) приймає тіло й параметри запиту в `POST /tasks`, `GET /tasks`, `PATCH /tasks/:id/status` та `:id` у шляхах. Некоректні дані мають давати `400 VALIDATION_ERROR` у єдиному форматі помилки (spec §3) і не потрапляти в БД (AC-2, AC-3, AC-4, AC-6, AC-10). Валідація належить `server/domain` (spec §2), а `domain` не може залежати від `fastify` чи будь-чого з `server/` (C3). Як валідувати вхідні дані декларативно, однаково для всіх маршрутів і без зайвих залежностей?

## Considered Options

- Ajv (вбудований у Fastify 5) + JSON Schema, схеми в `server/domain`
- Окремий пакет `ajv` + `ajv-formats` прямо в `domain`
- Ручна перевірка полів
- Joi / Zod

## Decision Outcome

Обраний варіант: «Ajv (вбудований у Fastify 5) + JSON Schema», бо він не додає окремої залежності, а перевірка декларативна й однакова для всіх маршрутів. Схеми лежать у `server/domain/schemas.js` як звичайні об'єкти без імпортів, а Fastify (ADR 0002) перевіряє за ними тіло й параметри запиту. `routes` імпортує з `domain` лише `schemas.js` і `errors.js`. Це явно дозволено в spec §2 і перевіряється C3 (ADR 0006). Порядок перевірок описує spec §5 S1: спершу схема у Fastify, потім правила в `domain`, потім існування `courseId` у `services`.

Правила, які JSON Schema не виражає, перевіряє код у `server/domain`: довжина `title` 3..120 символів після `trim` (AC-2) і `dueAt` у майбутньому відносно інжектованого `now` (AC-3, spec §3). Існування `courseId` (AC-4) потребує звернення до сховища, тож його перевіряє `CreateTaskCommand` у `services` через `CourseRepository.findById`, бо `domain` не залежить від портів сховища (spec §2). Помилки Ajv мапляться у `400 VALIDATION_ERROR` (spec §3).

Альтернатива «окремий пакет `ajv` + `ajv-formats` прямо в `domain`» відхилена як дублювання того, що вже дає Fastify. Ручна перевірка — більше імперативного коду й ризик неоднакової поведінки маршрутів; Joi / Zod — зайва залежність (C9).

### Consequences

- Добре, бо немає нової залежності: Ajv приходить разом із Fastify (C9).
- Добре, бо схеми — прості об'єкти без імпортів, тож `domain` лишається незалежним від `fastify` (C3), а `routes` бере з `domain` лише схеми й помилки.
- Добре, бо некоректні запити відсікаються до виклику сервісу, тож у БД нічого не записується (AC-2, AC-3).
- Добре, бо правила, що залежать від часу, використовують інжектований `now` і лишаються детермінованими в тестах.
- Погано, бо валідація розділена на три місця (схема Ajv, код у `domain`, `CreateTaskCommand` для `courseId`), і треба пам'ятати, яке правило де перевіряється; порядок зафіксовано в spec §5 S1.
- Погано, бо формат помилок Ajv треба явно мапити в `{ "error": { "code": "VALIDATION_ERROR", "message" } }`, інакше Fastify поверне власний формат.
