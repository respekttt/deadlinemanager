# bun:test як тест-раннер і вбудоване покриття

- **Date:** 2026-10-14

## Context and Problem Statement

Кожен критерій прийняття зі spec §6 має тест із назвою `AC-N:`, а окремий критерій запускається `make ac ID=AC-N` (`bun test -t "AC-N:"`). Потрібні unit-тести `domain` і `services` та API-тести через `app.inject()` (spec §2), а також поріг покриття рядків ≥ 80 % (C6). Яким тест-раннером це зробити без важких залежностей і окремої конфігурації?

## Considered Options

- `bun:test`
- Jest
- Mocha (+ Chai, nyc/c8)

## Decision Outcome

Обраний варіант: «`bun:test`», бо він вбудований у runtime (ADR 0001): не треба встановлювати важкі зовнішні бібліотеки, налаштовувати трансформацію ESM чи окремий інструмент покриття, а тести запускаються миттєво. Покриття вимірює вбудований `bun test --coverage` з порогом у `bunfig.toml` (C6).

### Consequences

- Добре, бо `make test` (C4), `make ac ID=AC-N` і `make coverage` (C6) — це той самий `bun test` з різними прапорцями.
- Добре, бо фільтр `-t "AC-N:"` дає запуск одного критерію, а наявність тесту для кожного AC перевіряє C5.
- Добре, бо Jest-подібний синтаксис (`describe`, `test`, `expect`) знайомий людям і ШІ.
- Добре, бо нуль додаткових devDependencies для тестів — менше роботи для `bun audit` (C9).
- Погано, бо `bun:test` реалізує не все з API Jest, а екосистема плагінів і репортерів менша.
- Погано, бо покриття від Bun рахується інакше, ніж у `c8`/`istanbul`, тож цифри можуть відрізнятися від звичних інструментів.
