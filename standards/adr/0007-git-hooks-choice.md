# Git-хуки в .githooks через core.hooksPath

- **Date:** 2026-10-14

## Context and Problem Statement

Швидкі перевірки (C1–C3) мають запускатися перед кожним комітом, а тести й smoke (C4, C5, C7) — перед кожним push (standards/checklist.md). Хуки в `.git/hooks` не версіонуються й не поширюються через репозиторій, тож кожен розробник мав би ставити їх вручну. Як зробити хуки спільними й увімкненими автоматично без зайвої залежності?

## Considered Options

- Власна тека `.githooks` + `git config core.hooksPath`, яку вмикає скрипт `prepare` у `package.json`
- Husky
- Ручні скрипти в `.git/hooks`

## Decision Outcome

Обраний варіант: «Власна тека `.githooks` + `git config core.hooksPath`», бо хуки поширюються через репозиторій і вмикаються автоматично на `bun install` скриптом `prepare` (`git config core.hooksPath .githooks || true`; `|| true` — щоб встановлення не падало поза git-репозиторієм), без зайвої залежності. Хуки лише викликають цілі `Makefile` (ADR 0008): `pre-commit` = `make check` (C1–C3), `pre-push` = `make prepush` (C4, C5, C7).

### Consequences

- Добре, бо хуки версіонуються разом із кодом і однакові в усіх.
- Добре, бо немає Husky у залежностях — менше роботи для `bun audit` (C9) і менше конфігурації.
- Добре, бо хук — це один рядок із викликом `make`, тож логіка перевірок не дублюється між хуками й CI.
- Погано, бо хуки можна обійти (`--no-verify`) або вони не ввімкнуться, якщо `bun install` запускали поза git-репозиторієм; тому остаточною гарантією лишається CI (`make ci`).
- Погано, бо скрипти хуків мають бути виконуваними й працювати в shell на всіх ОС розробників (зокрема Windows через Git Bash).
